# Besat — Failure Mode / Outage Matrix

Grounded in `ARCHITECTURE.md`. Because almost no production infrastructure
exists yet (§0 of that document), most rows below have honest gaps in
Detection/Prevention/Alert/Test — that is the actual finding, not an
oversight in this table. Columns: **Failure · Root cause · Affected
component · User impact · Severity · Detection · Prevention · Automatic
mitigation · Manual recovery · Alert · Test · RTO · RPO · Status**.

Severity: **P1** site-down/data-risk, **P2** major degradation, **P3** minor/
partial. RTO/RPO are targets to design toward, not measured facts, unless
marked "measured".

## Cascading-failure scenarios (worked examples)

1. **DB disk fills → DB refuses writes → backend 500s on every data
   endpoint → ~~health check still says "ok" (doesn't check DB)~~ *(fixed
   this session — the health check now correctly reports 503 once the DB
   is unreachable)* → but nothing pages anyone yet, since no alerting
   exists → the outage is now correctly *detectable* by anything that
   polls `/api/health/`, but still persists until a human happens to
   check.** This chain now touches three remaining gaps (disk monitoring,
   alerting, backup/restore) instead of four — closing the health-check
   blind spot removes the worst part of this scenario (an outage that
   looked healthy from the outside) but the other gaps are still open.
2. **Traffic spike (registration day) → 6 concurrent worker/thread slots
   saturate → requests queue → `GUNICORN_TIMEOUT=60` starts killing
   long-waiters → frontend's own BFF proxy calls time out → users see a
   generic error with no indication of *why* → no alert fires → the first
   signal anyone gets is a parent complaint.** This is the traffic-spike +
   observability gap compounding.
3. **A future real payment-gateway integration times out mid-checkout →
   without a proven idempotency/retry design (Phase 4, not yet built for
   this not-yet-existing integration) → risk of double-charge or an order
   stuck in an inconsistent state.** Flagged now, before it's built, so the
   idempotency design is a precondition for shipping a real gateway, not a
   retrofit after an incident.
